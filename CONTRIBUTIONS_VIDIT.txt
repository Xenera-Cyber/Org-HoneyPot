 1. rag_engine.py  (xynera-ai/)
--------------------------------------------

WHAT THE FILE DOES
  The RAG (Retrieval-Augmented Generation) Engine is the core
  intelligence module of the Xynera AI backend. When an attacker
  types a command inside the honeypot, the RAG engine:
    1. Checks whether the command can be answered instantly by a
       local simulator (no LLM call needed).
    2. Looks up the response cache to avoid duplicate API calls.
    3. Retrieves the most relevant reference document from the
       vector store / knowledge base.
    4. Constructs a detailed, persona-aware prompt and calls the
       Groq LLM API (llama-3.1-8b-instant by default).
    5. Cleans the raw LLM output, applies guardrails, caches the
       result, and returns the final deceptive response.

WHAT CHANGED / WAS BUILT
  * Local Command Simulation Layer (simulate_command_locally)
    Added a zero-latency local handler for the most common
    commands: pwd, whoami, hostname, id, groups, history -c,
    clear, echo (with dollar-variable expansion), and silent-
    success commands (chmod, mkdir, touch, rm, mv, cp, cd).
    These are intercepted before any LLM call, dramatically
    reducing latency and Groq API quota consumption.

  * Connection Pool (httpx.AsyncClient)
    Replaced per-request HTTP clients with a single shared
    AsyncClient instance. This reuses TCP/TLS sessions and cuts
    per-request overhead.

  * Response Cache (_response_cache)
    Implemented an in-memory dict keyed on
    (command, username, hostname, cwd). Repeated commands from
    the same session persona are served instantly from cache.

  * Rate-Limit and Retry Logic (call_groq_api)
    Added exponential back-off retry logic (up to 6 attempts)
    that correctly parses the "try again in Xs" message from the
    Groq 429 response body, sleeps exactly the required time,
    then retries. Transient 5xx errors also trigger back-off.

  * LLM Output Cleaner (clean_llm_output)
    Built a regex-based post-processor to strip markdown code
    fences, leading shell prompts, echoed command lines, and
    trailing prompt characters that the LLM sometimes adds.

  * Dynamic RAG Context Lookup (retrieve_context)
    Extended the context-retrieval logic to first search for
    session-specific, dynamically generated data (employee CSV,
    AWS credentials, SSH keys, emails, etc.) before falling back
    to the static knowledge base. COMMAND_TO_DATA_KEY maps 30+
    sensitive file paths to their generated data keys.

  * Dynamic Config Integration
    The engine reads dynamic_config.json at runtime to check
    ragEnabled and guardrailsEnabled flags. If RAG is disabled
    from the dashboard, the LLM is still called but without
    any retrieval context. Guardrails can similarly be toggled
    without restarting the backend.

  * Per-Persona Filesystem State Injection
    Three environment-aware filesystem descriptions
    (ubuntu-server, staging-api-01, backup-node-02) are injected
    into the LLM prompt so that ls, cat, and find commands return
    a consistent, coherent fake directory tree for each persona.

  * generate_deception() helper
    Added a lightweight wrapper used by the honeypot's command
    router to call the RAG engine without needing to construct
    a full attacker profile externally.

 2. knowledge_base.py  (xynera-ai/)
--------------------------------------------

WHAT THE FILE DOES
  The Knowledge Base is a curated static library of Linux command
  reference documents. Each document is a dictionary containing:
    - "command"        - the exact command string
    - "description"    - one-line human-readable description
    - "example_output" - a realistic sample terminal output

  These documents are loaded by the vector store (TF-IDF + FAISS)
  and used as reference examples by the RAG engine when generating
  responses.

WHAT CHANGED / WAS BUILT
  * Core Command Library (static entries)
    Hardcoded realistic outputs for approximately 35 Linux
    commands including:
    ps, netstat -antp, ls, whoami, uname, nmap, top, ip,
    ifconfig, id, ss, df, free, curl, wget, chmod, mkdir, ping,
    uptime, systemctl, env, lscpu, history, nc, sudo, find,
    grep, w, last, crontab, iptables, hostname, dmesg,
    lsb_release, which, docker, netcat.

  * Dynamic Data Integration
    Connected the knowledge base to data_generator.py so that all
    documents referencing real-looking sensitive files use the same
    per-session randomised data that the session_manager generates.
    This ensures consistent cat command output across the session.

  * Sensitive File Documents (30+ entries added)
    Added new document entries for high-value files attackers
    routinely look for:
      - SSH private keys (/home/ubuntu/.ssh/id_rsa, backup_key)
      - /etc/shadow, /etc/passwd
      - AWS credentials + config
      - Kubernetes kubeconfig
      - .pgpass, .env, Slack config.json
      - Stripe secret key (stripe_config.json)
      - Kubernetes deployment YAML (k8s_deployment.yaml)
      - Database backup SQL dump
      - Nginx config, Redis config, PostgreSQL config, sshd_config
      - Netplan config, /etc/hosts

  * Email Decoy Documents (5 new entries)
    Added 5 corporate email files:
    inbox_summary.txt, security_phishing_alert.txt,
    staging_db_access.txt, performance_review_cycle.txt,
    vendor_contract_renewal.txt
    Seeded with per-session employee names for realism.

  * 21 Internal Markdown Documents
    Added dynamically generated entries for security reports,
    meeting notes, VPN guidelines, API gateway docs, incident
    reports (DDoS, phishing, malware, data leak), HR documents,
    contracts, and network topology guides.

 3. data_generator.py  (xynera-ai/)
--------------------------------------------

WHAT THE FILE DOES
  The Data Generator creates a complete, internally consistent,
  per-session fake corporate identity for the honeypot. Every
  new attacker session gets a unique but believable set of:
    - 25 named employees (IDs, emails, roles, departments,
      access levels, phone numbers, assigned projects)
    - Department registry (6 departments, budgets, locations)
    - 5 active/completed projects with leads and budgets
    - Client and vendor lists
    - Infrastructure asset inventory (YAML)
    - Fake credentials (SSH keys, AWS keys, .env variables,
      Stripe keys, Kubernetes secrets, PostgreSQL passwords)
    - System log files (auth.log, syslog, audit_log.csv)
    - Corporate email messages
    - 21 internal markdown documents

  The seed is derived from the current weekday so that data
  is deterministic within a given day but rotates week-over-week.

WHAT CHANGED / WAS BUILT
  * Employee Generation Engine
    Built a fully randomised 25-person employee roster with:
    - Unique name collision avoidance
    - Pinned entry for "Fiona Garcia" (Security Engineer) to
      align with security incident reports that reference her
    - Role-based access levels (Admin / User / Restricted)
    - Manager hierarchy linking correctly to department heads

  * Credential and Secret Generation
    Implemented generate_credentials() which produces:
    - RSA-format SSH private key blocks (fake but realistic)
    - /etc/shadow entries with realistic bcrypt-format hashes
    - AWS access key IDs and secret keys (AKIA... format)
    - Kubernetes kubeconfig with cluster/user/context blocks
    - .pgpass file entries
    - Netplan YAML network config
    - .env file with DATABASE_URL, SECRET_KEY, REDIS_URL, etc.
    - Slack webhook URL and channel config JSON
    - Stripe publishable + secret key pair

  * Infrastructure YAML Generation
    Generates a realistic 5-node infrastructure inventory in
    YAML format listing hostnames, IPs, OS versions, open ports,
    environment (prod/staging), and patch status.

  * Database Backup SQL
    Produces a realistic SQL dump with CREATE TABLE and
    INSERT INTO statements for users, orders, products tables
    populated with per-session random data.

  * 21 Markdown Document Generator
    Generates all internal corporate documents as markdown
    strings populated with the current session's employee names,
    project codes, and credential values so all documents are
    mutually consistent.

  * Email Generator
    Produces 5 corporate emails referencing real employee names
    from the same session.

  * get_generated_all() - main entry point
    Wraps all generators under a single call with a weekday-based
    random seed, returns one consolidated dict used by both
    knowledge_base.py and attacker_profile.py.

 4. api_server.py  (xynera-ai/)
--------------------------------------------

WHAT THE FILE DOES
  The API Server is the HTTP gateway of the Xynera AI backend.
  It exposes two endpoints:
    GET  /health   - liveness check used by ai_client.py
    POST /process  - full command-processing pipeline

  The /process endpoint orchestrates the entire AI pipeline in
  a single request-response cycle.

WHAT CHANGED / WAS BUILT
  * Full Pipeline Orchestration
    Built the 8-step processing pipeline:
      1. Classifier    - classifies command, returns risk score
      2. Session data  - updates per-session command history
      3. Attacker Profile - builds/updates per-IP profile
      4. Threat Engine - computes cumulative threat level
      5. Personality   - selects honeypot persona for session
      6. RAG Engine    - generates the deceptive AI response
      7. Predictive Engine - forecasts next attacker action
      8. Logger        - writes structured logs (4 log types)

  * ProcessRequest / ProcessResponse Models (Pydantic)
    Designed the full request schema:
      ip, command, session_id, history, local_attack_type,
      cwd, hostname, username
    And the response schema:
      reply, attack_type, personality_name, hostname,
      username, prediction, threat_score

  * Prediction Result Integration
    Wired predictive_intelligence() output into both the
    /process response payload AND the centralised logger, so
    predictions (next action, high-value target, session outcome)
    are surfaced to the dashboard and stored in the log.

  * Multi-Type Logging
    Calls four different log functions per request:
    log_personality_integration, log_ai_decision,
    log_ai_analysis, log_centralized_event - giving the
    dashboard access to rich, structured event data.

 5. vector_store.py  (xynera-ai/)
--------------------------------------------

WHAT THE FILE DOES
  The Vector Store indexes all knowledge-base documents with
  TF-IDF vectors and FAISS (Facebook AI Similarity Search) for
  fast nearest-neighbour retrieval. It answers the question:
  "Given this attacker command, which reference document is the
  most relevant?"

WHAT CHANGED / WAS BUILT
  * Custom TF-IDF Vectorizer (TFIDFVectorizer class)
    Built from scratch (no sklearn dependency):
    - Tokenises text with a regex word-boundary splitter
    - Removes a curated English stopword list
    - Computes IDF weights across the corpus
    - Produces L2-normalised float32 vectors

  * FAISS IndexFlatIP (inner-product / cosine similarity)
    Builds a FAISS index over all KB document embeddings and
    performs single nearest-neighbour search per query.

  * Disk Cache with Hash Invalidation
    Saves the built index + metadata to .cache/ on disk.
    On startup, computes an MD5 hash of the knowledge base
    content. If the hash matches the cached version, the index
    is loaded from disk (fast start-up). If the knowledge base
    changed, the index is rebuilt automatically.

  * Command Synonym Expansions (COMMAND_EXPANSIONS)
    Added a 40-entry synonym dictionary that boosts semantic
    recall for abbreviated Linux commands. For example,
    "df" expands to "disk free space usage filesystem disk space
    usage". Documents are indexed with (command x3) + expansions
    + description to give the command name the most weight.

  * Vocabulary Coverage Ratio Guard
    Before running FAISS search, computes what fraction of query
    tokens exist in the vectorizer vocabulary. If the first token
    is a known command, the ratio is boosted to 0.8 or higher.
    Queries with less than 50% vocabulary coverage skip the FAISS
    call, preventing false positives on unknown commands.

 6. config.py  (xynera-ai/)
--------------------------------------------

WHAT THE FILE DOES
  Central configuration module. Reads static variables
  (SERVER_HOST, SERVER_PORT, LOG_FILE, GROQ_API_KEY, GROQ_MODEL)
  and exposes get_dynamic_config() which merges defaults with
  the live dynamic_config.json file on every call.

WHAT CHANGED / WAS BUILT
  * Manual .env Parser (fallback GROQ_API_KEY loader)
    Added a pure-Python .env parser as a fallback when
    python-dotenv is not installed. Reads the local .env file
    line by line, strips comments and quotes, and extracts
    GROQ_API_KEY - removing the hard dependency on dotenv.

  * get_dynamic_config() Function
    Implemented a runtime-reload function that:
    - Defines a safe set of defaults for all AI parameters
    - Reads dynamic_config.json from the same directory
    - Deep-merges the file over the defaults
    - Falls back silently to defaults on any JSON parse error
    This is called on every API request, so dashboard changes
    to model, temperature, RAG toggle, etc. take effect
    immediately without restarting the backend.

 7. predictive_engine.py  (xynera-ai/)
--------------------------------------------

WHAT THE FILE DOES
  The Predictive Engine analyses the current session's threat
  metrics and produces actionable forecasts about attacker
  behaviour, returned in every /process API response and logged
  for dashboard display.

WHAT CHANGED / WAS BUILT
  * predictive_intelligence()
    Core function called once per command. Takes:
      - curiosity_score   (from attacker profile)
      - risk_score        (from threat engine)
      - engagement_level  (LOW / MEDIUM / HIGH)
    Returns a dict with four predictions:
      1. next_probable_action
         (Reconnaissance / Credential Access / Privilege Escalation)
      2. high_value_target
         (Public Directories / Sensitive Files / Admin Credentials)
      3. deception_success_probability  (51% / 74% / 92%)
      4. session_outcome
         (Low / Medium / High Risk Session)

  * bait_recommendation()
    Analyses a per-session asset-access frequency dict and
    identifies the most attractive honeypot asset along with
    total access counts. Designed for future dashboard
    bait-tuning features.

  * deception_effectiveness_report()
    Generates a structured performance summary of the deception
    pipeline (most successful trap, highest engagement session,
    AI prediction accuracy).

  * performance_analytics()
    Accepts live system metrics (AI response time, CPU, RAM,
    detection accuracy) and produces an optimisation report with
    status labels and actionable recommendations.

WHAT THE FILE DOES
  Runtime configuration file that can be edited live (or updated
  by the dashboard Settings panel) to change system behaviour
  without restarting any service.

  xynera-ai/dynamic_config.json  controls the AI backend.
  xynera-honey/dynamic_config.json controls the honeypot server.

WHAT CHANGED / WAS BUILT
  xynera-ai/dynamic_config.json fields:
    personality         : "auto" - engine selects persona based
                          on threat level automatically
    model               : "llama-3.1-8b-instant" - active LLM
    confidenceThreshold : 85 - minimum confidence for AI routing
    temperature         : 0.1 - low for deterministic output
    maxContext          : 4096 - maximum LLM context window

    maxConcurrentSessions : 50
    sessionTimeoutMinutes : 30
    logRetentionDays      : 30
    maxCommandsPerSession : 250
    sshEnabled / httpEnabled / ftpEnabled : service toggles

 SECTION 2 - AI DASHBOARD INTEGRATION
--------------------------------------------------------------

Designed and integrated a full-stack monitoring dashboard
connecting the React frontend (UIprogress/dashboard-integrated)
to live backend data via the Dashboard API.

KEY COMPONENTS BUILT / INTEGRATED

  * ai_client.py  (xynera-honey/)
    The bridge between the honeypot server and the AI backend.
    Built with:
    - Persistent HTTP session (requests.Session) for connection
      pooling across all attacker sessions
    - Background health-monitor daemon thread (threading.Event)
      that polls /health every 5 seconds. Transitions are logged
      on state change (Online / Offline) without log spam.
    - Fast-path: if the monitor marks the backend offline,
      send_to_ai() returns an offline fallback immediately
      without burning retry budget or introducing latency
    - 2-retry loop with 0.5s back-off on ConnectionError
    - 5-second hard timeout, with Timeout exceptions aborting
      immediately rather than retrying (prevents cascading load)
    - clean_response() helper strips markdown fences from AI
      output before returning it to the attacker terminal
    - Made hostname/username of the attacker's shell fixed for
      the session lifetime (not overridden by AI output)

  * dashboard_api.py  (xynera-honey/)
    Full-featured FastAPI service serving the React dashboard.
    Key endpoints and features:
    - CORS middleware allowing the React dev server to query
    - No-cache HTTP headers on every response (real-time data)
    - Log parsing with compiled regex (LOG_PATTERN) to extract
      structured fields from AI backend log files
    - Geo-mapping of attacker IPs to mock locations with
      hash-based consistency (same IP = same country always)
    - Service status checks (is_port_open) for the honeypot,
      AI backend, and dashboard API health cards
    - Uptime counter from server start time
    - psutil integration (optional) for CPU/RAM metrics
    - All dashboard widgets backed by live data:
        /api/stats          - total events, active sessions,
                              threat level, uptime
        /api/recent-events  - last N log entries parsed
        /api/attackers      - per-IP session summaries
        /api/geo-map        - lat/lon for attack origin map
        /api/service-status - health of all three services
        /api/config         - read dynamic_config.json
        PUT /api/config     - write dynamic_config.json (live
                              settings panel in dashboard)

  * React Dashboard (UIprogress/dashboard-integrated/)
    - Real-time event log with colour-coded severity levels
    - Active session list with per-session threat scores
    - Geographic attack-origin map
    - AI model and deception-pipeline settings panel
    - Prediction panel showing next probable attacker action
    - All data polled from dashboard_api.py at configurable
      intervals with no page reload required

 SECTION 3 - COMPATIBILITY WORK
--------------------------------------------------------------

Made the following compatibility fixes across the codebase:

  * Removed hard python-dotenv dependency - replaced with a
    custom .env parser in config.py so the AI backend runs
    on any Python 3.9+ environment without extra packages.

  * Made vector_store.py start-up silent on missing cache -
    init_vector_store() is called lazily on first search() call,
    so importing the module does not trigger any side effects or
    errors if the .cache/ directory does not exist yet.

  * Unified the session_id flow - the classifier assigns a
    session_id per IP, which is threaded all the way through
    the API pipeline (api_server -> rag_engine ->
    attacker_profile -> knowledge_base) so all modules reference
    the same session.

  * Fixed cwd defaulting - when no cwd is provided by the
    honeypot, the RAG engine defaults to /home/ubuntu or
    /home/dev based on the active username, preventing
    inconsistent LLM outputs about the current directory.

  * FAISS float32 dtype enforcement - added explicit .astype()
    calls on all numpy arrays passed to FAISS to prevent the
    "array type is not float32" crash on platforms where numpy
    defaults to float64.

  --------------------------------------------------
  GET  /api/stats            - verified uptime, event counts
  GET  /api/recent-events    - verified log parsing and format
  GET  /api/attackers        - verified IP grouping

SECURITY OBSERVATIONS NOTED DURING TESTING
